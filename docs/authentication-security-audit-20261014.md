# PlaceAI authentication and authorization audit - 14 October 2026

Scope: custom FastAPI authentication, browser credentials, Google identity binding,
password recovery, database-backed limits, roles, institution boundaries and protected
feature access. Supabase hosts the database; Supabase Auth is not this application's
identity provider. Payments remain deferred. No real student's password, report or
session was changed during attack testing.

## Findings and fixes

### 1. Access tokens survived logout - Medium

Affected: `app/routers/auth.py:logout`, `app/dependencies.py:get_current_user`.
Previously logout revoked one refresh JTI, but a copied access token stayed usable
for its remaining lifetime. An attacker who obtained that token could keep reading
the victim's APIs after the victim signed out.

Logout now invalidates the account's authentication version and every refresh session,
with a locked user update. Both cookie-based browser logout and bearer-only API logout
are supported. Old tokens fail the existing server-side version check immediately.
This intentionally signs out other devices too. Malformed or revoked credentials do
not revoke somebody else's sessions. Tests exercise multiple old access/refresh
credentials and forged logout credentials.

### 2. Combined IP/email limits were independently bypassable - Medium

Affected: `app/rate_limit.py`, login/form/JSON/role routes, Google password linking,
signup, recovery and new verification/MFA endpoints.
The previous key combined account and IP. Rotating IPs reset an account's attempt
budget; changing emails reset an address's budget during password spraying.

Separate durable address and account budgets now supplement the original combined
budget. Account cooldowns are capped at five minutes, and blocked requests do not
extend them. The address budget permits shared college networks, but is not a
volumetric DDoS control. Tests rotate IPs and accounts and verify HTTP 429. Unknown
password-login accounts now perform a dummy Argon2 verification to reduce obvious
account-existence timing differences. Inactive accounts use the same password-login
failure as invalid credentials.

### 3. Password composition alone did not reject compromised credentials - Medium

Affected: `app/utils.py:get_hashed_password`, `app/password_security.py`, password
schemas and matching browser validators.
An attacker could reuse a known breached password that met the previous character
requirements. All newly chosen passwords now pass a local common-password rejection
and, in production, the owner's explicitly approved HIBP k-anonymity check. Only the
first five SHA-1 characters go over HTTPS to `api.pwnedpasswords.com`; neither the
password nor its full hash is sent. SHA-1 is used only for this lookup, not storage.
Responses are padded, bounded, validated and cached by prefix for at most ten minutes.
Production password-setting fails closed when screening is unavailable; existing
password sign-in remains available. Random Google bootstrap credentials skip this
check because they are generated by the server and never disclosed.

Argon2id remains the storage algorithm (all 20 production accounts checked use it).
Passwords allow up to 128 characters; varied 20+ character passphrases can omit
mandatory character classes. The existing 12+ character mixed-class alternative is
retained for provisioning compatibility. Browser and server validation both support
these paths. Validation responses no longer echo submitted passwords or OTP inputs.
Tests cover breached rejection, service outages, passphrases and five-character-only
disclosure. A known public test phrase was detected by the real official range API.

### 4. New public password accounts had no email-ownership gate - Medium

Affected: `auth.signup`, `dependencies.get_current_user`, `app/auth_protection.py`.
Previously a person could register an email address without demonstrating ownership
and use the workspace. New production public accounts now receive a backend-owned
verification-required flag and a one-time email link. Public signup returns the same
HTTP 202 message for new accounts and duplicate email/usernames; a throttled public
resend operation also returns a generic response. Password sign-in issues no session
until the random, hashed, 15-minute, single-use email link is consumed. A server-side
workspace gate additionally rejects any stale or otherwise issued unverified token.
Changing frontend state, a role cookie or the user payload cannot clear this flag.
Verification delivery failure is surfaced, not treated as successful verification.
Verified Google identity and a successful recovery link also prove mailbox control.

Existing college-provisioned and historical accounts are not silently reclassified or
locked out. Their actual `email_verified` status is reported accurately; an optional
verification action is available. Therefore this audit does NOT claim every historical
mailbox has been verified. Production email was already configured; tests use a
synthetic mail transport rather than emailing students.

### 5. Administrator accounts had no application second factor - Medium

Affected: all initial password and Google token-issuance paths; new account-protection
API and browser dialog.
A stolen administrator password previously sufficed to sign in. Opt-in RFC 6238
authenticator MFA is now available, recommended for administrators. Enrolment needs a
verified email, current password and a valid authenticator code within ten minutes.
Secrets are Fernet-encrypted, bound to the user ID, and never returned after setup.
Login issues only a random five-minute challenge until a valid second factor succeeds.
The challenge is hashed, version-bound and consumed with a database row lock. OTPs
expire with a 30-second step, allow one adjacent step for clock skew, and cannot be
replayed. Eight random 128-bit recovery codes are shown once and stored only as hashes;
each is consumed atomically. Disabling MFA needs current password and a current factor
or unused recovery code. Enabling/disabling revokes old sessions. Password reset does
not disable an enrolled authenticator. Controlled-login alerts/audit events are emitted
after successful MFA, not merely after password validation.

Tests exercise all password routes, Google enforcement, challenge expiration, wrong
codes/passwords, recovery reuse and mobile enrolment/sign-in. Six RFC test vectors
verify the TOTP algorithm. PostgreSQL concurrent requests verify exactly one challenge,
recovery-code and refresh-token success.

**Operational follow-up:** the two existing administrators must enrol their own
authenticators and safely save recovery codes. No factor was silently enabled on a real
account. TOTP is not phishing-resistant; passkeys or enforced managed-IdP MFA remain
appropriate future hardening. The encryption key is domain-separated from the existing
server signing secret; signing-secret rotation must include an MFA encryption migration.

### 6. Signed Google nonce cookies could be restored and replayed - Medium

Affected: `app/google_login.py:authenticate`.
The signature and expiry validated a nonce but did not consume it server-side. A client
holding the original cookie and ID token could replay them before expiry.
Nonce consumption is now a unique, conflict-safe database insert in the same transaction
as account binding/session issuance. Restoring the old cookie fails; failed account
binding rolls back rather than leaving a partially linked identity. Existing issuer,
audience, verified-email, subject binding and non-authoritative-domain password checks
remain. Unverified existing accounts additionally require explicit local-password proof
or email recovery before Google linking; existing passwords are not silently replaced.
Tests verify replay rejection, explicit linking and transactional rollback.

### 7. Public institution codes granted unapproved sponsored access - High

Affected: `app/student_entitlements.py:student_access_status`; downstream preparation
and Career Roadmap access.
Public signup accepted an institution code, and any resulting organization ID was
treated as institution sponsorship. A student could supply another college's code to
gain protected features without college approval.
Sponsorship now requires a server-verified student profile, matching user/profile
institution IDs and an active institution. The existing institution-admin approval
and provisioning routes own this verification flag. Disabling an institution also
removes its sponsorship. Verified, active college memberships retain access.
Tests reproduce self-claimed codes, expire the independent trial, then show access is
granted only after authorized verification and denied again for an inactive college.
This change fixes access control; it neither activates nor integrates payments.

### 8. Recovery credentials persisted in browser session storage - Low

Affected: `app/static/ui-state-fixes.js`, mirrored public asset.
The one-time recovery token was persisted in sessionStorage, making it recoverable by
later same-origin script execution. It now remains only in page memory, is removed from
the address bar, and clears any value left by an older version. Reloading requires
reopening the original email link. Token-bearing landing responses use `no-referrer`.
Browser tests cover storage absence, reload behaviour and working password validation.
Memory-only credentials still require XSS prevention; they are not immune to active XSS.

### 9. Recovery mail latency exposed an account-existence timing signal - Low

Affected: `auth.forgot_password` and its delivery helper.
The response body was generic, but only existing accounts synchronously waited on mail
delivery. Delivery now runs after the generic HTTP response in a separate DB session.
On transport failure, the previous link is restored only if a newer request has not
replaced it. Hashed 15-minute reset tokens, locked one-time consumption and session
revocation remain. Reset also completes temporary-password rotation. Tests verify
generic responses, safe delivery telemetry and prior-link preservation.

## Existing controls reviewed

- Browser access tokens are memory-only. Persistent refresh cookies are HttpOnly,
  Secure in production, SameSite=Lax and scoped to `/auth`; Google nonce cookies are
  SameSite=Strict. Refresh JTIs are stored server-side and rotated once under row locks.
- Protected API routes use backend identity dependencies. Roles come from the database,
  not frontend role fields or arbitrary JWT role claims. Platform/admin self-signup is
  rejected. Recruiter self-registration remains controlled.
- Student-owned profiles, notebooks, media and reports use owner/tenant lookups. Existing
  role, cross-institution, interview, file/export and offer-authority attack regressions
  remain in the suite. A route inventory checks every documented protected operation
  against a small explicit public allowlist.
- Browser cookie-mutation authentication requests reject foreign/null origins and
  cross-site fetch metadata. Workspace operations use bearer authorization, not implicit
  cookie authorization. Credentialed CORS is restricted to configured HTTPS origins.
- Production readiness rejects weak/equal signing secrets, SQLite, debug token disclosure,
  automatic schema creation and insecure origins. Docs/OpenAPI, uploaded paths and
  private artifacts are unavailable publicly. HSTS, CSP, frame denial, MIME protection
  and authenticated no-store headers are checked on all deployed hosts.
- Supabase security advisors returned no lints. None of the 47 existing public tables
  was accessible to browser `anon` or `authenticated` roles. The new protection table has
  RLS, no public/browser grants and an explicit restricted Render runtime policy.

## Verification and limits

Evidence is collected in isolated tests, bounded anonymous live HTTP checks, dependency
and secret scans, CI and deployment-health checks. Local setup failures (an unavailable
browser binary, an inherited test environment flag and a short-lived PostgreSQL helper)
were diagnosed separately; failed/error runs are not counted as passes.

## Final control checklist

| Requested control | Evidence / outcome |
| --- | --- |
| Authentication bypass | Forged, invalid, expired/revoked and wrong-purpose credentials are denied in regression tests. |
| Frontend privilege changes | Roles are read from the database; modified role state/cookies do not grant platform access. |
| API authorization / IDOR | Explicit public-route allowlist plus role, ownership, tenant, media and report/export tests. |
| Sessions and logout | Memory-only access token, HttpOnly production cookie, one-time refresh and all-session logout revocation. |
| Email verification | New production public signup requires a single-use email link before password sign-in; generic registration/resend responses. Historical exceptions remain explicit. |
| MFA | Tested enrolment, challenge expiry, OTP/recovery replay protection, Google enforcement, disable reauthentication and PostgreSQL concurrency. Administrator enrolment remains a human step. |
| Brute force | Durable separate address/account budgets; new MFA challenges do not reset the account's OTP budget. |
| Password reset | Hashed expiring links, locked consumption, generic response, post-response mail, version/session revocation. |
| Password quality | Argon2id, common/breached rejection, approved k-anonymity API, bounded passphrases and outage policy. |
| Client-side secrets | Input-redacted validation errors, source/history secret scan, no persistent browser credential storage. |
| Production configuration | Bounded live headers/origin/private-artifact checks; database grants and RLS/advisors inspected. |
| Regression | Full-suite and focused browser/PostgreSQL checks are release gates; unsuccessful setup runs are not passes. |

Run the full suite with a dedicated `TEST_POSTGRES_URL` to exercise real row locks;
SQLite alone cannot validate concurrency. CI provisions PostgreSQL. Run the existing
security surface check with the released main SHA and verify canonical, Vercel and Render
health match that SHA. Run dependency audit, source/secret hygiene and required checks
before merging; do not disable the repository ruleset to release this work.

Remaining limits: optional MFA needs human enrolment; historical unverified accounts
remain explicitly legacy exceptions. Production signup/resend use generic responses;
development keeps explicit duplicate feedback for local test fixtures. The
recovery response avoids provider-latency disclosure, not every possible micro-timing
signal. Active XSS can act as a user even when refresh cookies are HttpOnly. MFA recovery
requires safely stored codes; no unaudited support bypass is added. HIBP/transactional
email availability, key custody, backups, incident response and external IdP controls
remain operational dependencies. This is not an independent penetration-test certificate
or a guarantee that every possible authentication/authorization attack is impossible.
